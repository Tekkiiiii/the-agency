# design-system — Brand Token SSOT

Layer 0 of the design stack. This directory is the single source of truth for brand
color, font family, and hard rules across every design/media skill in the system.

## The contract

**JSON is the source. CSS is generated. Never hand-edit `brands/*.css`.**

```
brands/*.json      SOURCE OF TRUTH — color, font family, brand ratios, hard rules
brands/*.css       GENERATED by build.js — :root { --brand-*: ...; } — do not edit
overlays/*.css     HAND-AUTHORED — layout, density, type scale, corner radius, motion
                    ZERO HEX. References var(--brand-*) only.
build.js           json -> css, plus the overlay hex lint
verify-semantic-consumers.js   renders CONSUMER css in a browser and proves the
                    semantic signals stay distinct after resolution
```

This split exists because a written brand SSOT is not enough on its own. In the
system this was extracted from, a hand-written brand guideline document had existed
for months and **85 skills drifted from it anyway** — by hand-copying hex into new
files. Generation removes the sync step; there is no second hand-maintained file to
fall out of sync.

## Why JSON, not CSS, is the source

Some consumers cannot read CSS custom properties at all. A `pptxgenjs` deck template
(`template.js`) hardcodes brand values as plain JS consts; so do Remotion-style video
compositions. JSON is readable from both CSS-generation and JS-`require()` consumers;
CSS alone is not.

## Consuming a brand (HTML/CSS consumers)

1. Pick a brand: `brands/{name}.css` (this repo ships `neutral`; add your own below)
2. Pick an overlay (optional — layout/motion only): `overlays/{editorial-minimal|contrast-dark|midcentury-warm|brutalist}.css`
3. Load the brand CSS **before** the overlay CSS — the overlay's `var(--brand-*)`
   references only resolve once the brand's `:root` block has defined them.
4. **For a self-contained deliverable** (any HTML file that must work standalone,
   e.g. `html-plan-style` output): do NOT `<link>` or `@import` these files live.
   Resolve the brand's `:root` values into a copied `:root` block **at generation
   time** — copy the actual CSS custom property declarations into the output file's
   own `<style>` block. A live reference to `design-system/` from a shipped
   deliverable would make that deliverable permanently dependent on this path,
   regressing any skill's self-contained guarantee.

## Consuming a brand (JS consumers, e.g. pptxgenjs decks)

```js
const path = require("path");
const brand = require(path.join(AGENCY_ROOT, "design-system/brands/neutral.json"));
const ACCENT = brand.colors[brand.roles.accent];
const INK    = brand.colors[brand.roles.ink];
```

`AGENCY_ROOT` resolves as `$AGENCY_HOME` → `$CLAUDE_CONFIG_DIR` → `~/.claude` —
see `../docs/INSTALL-LAYOUT.md`. Never hardcode an absolute path here.

## Canonical role schema

Every `brands/*.json` must populate a `roles` object mapping these 15 canonical
role names to a key in that same file's `colors` object. `overlays/*.css`
reference **only** these roles (as `var(--brand-{role})`) — never a brand's raw
color name, since raw names differ per brand.

| Role | Meaning |
|---|---|
| `bg` | Page/canvas background |
| `surface` | Card/panel background |
| `surface-alt` | Alternate section background |
| `border` | Divider/border color |
| `ink` | Primary text / dark foreground |
| `text-muted` | Secondary text, captions |
| `primary` | Dominant brand color — headings, CTAs |
| `primary-dark` | Darker variant of primary |
| `primary-light` | Lighter variant of primary — links, accents |
| `accent` | Focal/highlight color |
| `accent-dark` | Accent hover/active state |
| `secondary` | Supporting/secondary color |
| `secondary-dark` | Darker variant of secondary |
| `depth` | Depth accent only (footers, deep backgrounds, atmospheric glow source) — never a button hover or primary CTA fill unless the brand's own rules say otherwise |
| `text-on-primary` | Text color when rendered on the `primary` background |

Plus three font roles: `--brand-font-display`, `--brand-font-body`, `--brand-font-mono`.

## Semantic roles are functional, not brand expression

Every `brands/*.json` also carries a `semantic` block with exactly four roles —
`success`, `warning`, `danger`, `info` — each an `{ accent, text }` pair.

These are **signals**, not styling. They must stay mutually distinguishable no
matter which brand is loaded, including brands that own no red and no green.
`build.js` enforces this: the four `accent` values must be pairwise distinct or
the build fails.

Two rules that are easy to get wrong:

- **Never use an `accent` value as foreground text.** It is contrasted for
  borders and icons sitting on a light tint, not for text on that tint. Use
  `text` for anything a reader reads.
- **A brand with no dedicated hue still needs four distinct signals.** Record why
  each value was picked in that role's `note` field, so the next person does not
  "fix" it back into the brand palette and collapse two signals into one.

## Overlays never carry a hex — this is enforced, not a convention

`node build.js` greps every `overlays/*.css` for hex literals and fails the build
if it finds one. It also rejects **chromatic** decimal `rgb()` / `rgba()` values,
which evade a hex-only grep entirely — that blind spot shipped three real
brand-drift bugs before it was closed. Achromatic values (`r == g == b`) are
allowed, because a drop shadow is black under every brand.

If an overlay needs a derived tint or transparency the brand JSON doesn't provide,
use `color-mix(in srgb, var(--brand-*) N%, transparent)` — see
`overlays/midcentury-warm.css`'s atmospheric glow for the pattern. Never
pre-compute and hardcode a tint as a new hex value; that reintroduces exactly the
drift this system exists to prevent.

## Disambiguation: overlay vs. vendored taste skill

`overlays/brutalist.css` and the vendored `industrial-brutalist-ui` skill are one
edit away from being confused:

> Brand assigned → use `overlays/*.css` (brand-consistent, no color of its own).
> No brand yet, or fully exploratory → use the vendored taste skill directly
> (it owns its own palette — editing it is a silent fork that dies at the next
> upstream pull).

## Brands

| File | Source | Default for |
|---|---|---|
| `neutral.json` | none — deliberate generic fallback | Any work with no brand guidelines yet |

`neutral` is the only brand this repo ships, and that is on purpose: a brand file
is *your* (or your client's) intellectual property, not framework content.

### Adding your own brand

1. Copy `brands/neutral.json` to `brands/{yourname}.json`.
2. Fill in `colors` with your palette's raw named values, then map all 15 `roles`
   onto those names. Roles reference color **keys**, never literal hex — that
   indirection is what lets a role be renamed without touching every consumer.
3. Fill the `semantic` block. Four distinct accents, each with a readable `text`
   partner, each with a `note` recording the provenance of the pick.
4. Set `fonts.display` / `fonts.body` / `fonts.mono`.
5. Run `node build.js`. It validates the schema and generates
   `brands/{yourname}.css`. **Commit the generated CSS** — the drift check below
   depends on the generated output being in git.
6. Never hand-edit the generated `.css`. If a value is wrong, fix the JSON and
   re-run.

## Overlays

| File | Feel | Requires a brand where… |
|---|---|---|
| `editorial-minimal.css` | Airy, centered, flat, calm motion | `bg` is light — the least opinionated pick |
| `contrast-dark.css` | Dark canvas, TV/large-screen scale | `primary` is genuinely dark |
| `midcentury-warm.css` | Material-tactile, atmospheric glow, no shadows | `primary-dark` reads as a canvas and `depth` carries a warm hue |
| `brutalist.css` | Swiss print x military terminal, rigid grid | `border` and `ink` carry enough contrast to draw the grid |

Motion durations/easings in every overlay are sourced from `emil-design-eng`'s
documented ranges (button 100-160ms, tooltips/dropdowns 125-250ms, modals/drawers
200-500ms) rather than re-derived — see each overlay's Motion block for its pick
within that range and why.

## Overlays are NOT brand-agnostic — check before pairing

An overlay is layout + density + type scale + motion, and it is hex-free, so it
*looks* like it composes with any brand. It does not. An overlay that paints a
surface picks a **role** to paint it with, and whether that role's value is
actually suitable is a per-brand fact the role schema does not encode.

`contrast-dark.css` is the live example. It sets `body { background:
var(--brand-primary) }`. Against a brand whose primary is a deep indigo that
yields the intended dark canvas. Against a brand whose primary is a mid-tone blue
it yields a **mid-blue canvas** with light text on it. The overlay is not "dark"
in any brand-independent sense — it is dark *for brands whose primary is dark*.

This is measured, not theoretical. Rendering `contrast-dark` against a brand whose
primary was a mid-tone blue produced **8 of 15 text/background pairs failing WCAG
AA**, the worst being accent-on-card at **1.30:1**.

There is no `canvas` / `canvas-ink` role in the 15-role schema, so a brand cannot
currently declare "this is my dark surface" independently of `primary`. Until one
exists, **verify any new brand x overlay pairing by rendering and measuring it** —
do not assume hex-free means brand-portable. The "Requires a brand where…" column
above states each overlay's precondition; it is a starting point, not a proof.

## Verification

Run all three. The first two are cheap and should be in any pre-commit routine;
the third needs a browser.

```bash
# 1. No hex may live in an overlay, and generated CSS must match its JSON source
node design-system/build.js

# 2. Generated CSS is committed and has not drifted from the JSON
git diff --exit-code design-system/brands/*.css

# 3. Consumers actually RENDER distinct semantic signals (needs Playwright)
npm i -D playwright && npx playwright install chromium
node design-system/verify-semantic-consumers.js
```

Check 3 exists because checks 1 and 2 only look at the **source**. They cannot
catch a skill that never reads the source at all — which is precisely how a
plan-styling skill shipped with `--color-success` and `--color-warning` resolving
to the same blue while the source lint stayed green. Only a real browser resolves
the full `var()` / `color-mix()` chain, so only a real browser can prove it.
Targets not present in a given install are skipped, not failed.
